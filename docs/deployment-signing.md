# 배포 서명과 롤백 방지 명세 (SIGN)

2026-10-23 #0 결정. 정책 배경은 [배포·서명·업데이트 정책](release-policy.md) 2번. 형식은 [배포 규격](deployment-format.md)에 minor 2로 추가한다.
위협: 배포 링크(Drive 등)가 탈취되거나 교체되어 악성 모드가 배포되는 것, 그리고 옛 정상 배포로 되돌려 취약한 버전을 받게 하는 것(롤백).
범위 밖: 서명 키 자체의 탈취 방어, 런처 프로그램 업데이트 서명(RELEASE-02), 신선도(freeze) 공격 방어.

## 신뢰 구조
- Studio가 프로젝트마다 **Ed25519 키 쌍**을 만든다(Node `crypto` 내장, 새 의존성 없음). 개인 키는 프로젝트 폴더·내보내기 산출물에 넣지 않는다.
- 공개 키는 서버 구성 파일(`torchlauncher-server.json`, 런처 ZIP과 함께 전달되는 신뢰 채널)의 선택 필드로 들어간다:
  `"signing": { "algorithm": "ed25519", "publicKey": "<base64url, 32바이트>" }`. 알 수 없는 algorithm·길이 오류는 구성 거부.
- 런처는 구성에 `signing`이 있으면 **서명되지 않았거나 검증 실패한 배포를 모두 거부**한다(1.0/1.1 포함). `signing`이 없는 기존 구성은 지금처럼 무서명 1.0/1.1을 받는다(전환 기간). 새 Studio 내보내기는 항상 키를 만들어 넣는다.

## 컨테이너 1.2
`[64바이트 헤더][64바이트 서명][JSON 인덱스][페이로드]`. 헤더는 기존 레이아웃에서 minor = 2, flags = 0, 나머지 필드(indexLength, totalLength, 인덱스 SHA-256) 동일.
서명 구간이 추가되므로 페이로드 절대 위치는 `128 + indexLength + offset`, `totalLength`는 헤더·서명·인덱스·페이로드의 합이다.
브랜딩 확장 규칙(아이콘, 배경 이어 붙이기, 1.1의 검증)은 1.2에도 그대로 적용한다(1.2 = 서명 + 선택적 브랜딩).
reader는 정확히 1.0 / 1.1 / 1.2만 수락한다(미래 minor 거부 유지). 이전 런처는 1.2를 거부하므로 서명 도입 전 런처 업그레이드가 필요하다.

서명 대상 메시지: `"TORCHPACK-SIG-v1\0" || 헤더 64바이트`. 헤더가 인덱스의 SHA-256과 길이를 포함하므로 인덱스 전체가 간접적으로 서명된다. 검증 순서: 헤더(0–63)와 서명(64–127) 읽기 → 인덱스 읽기 → SHA-256이 헤더와 일치 → 서명 검증 → 그 뒤에 인덱스를 신뢰하고 파싱·사용. 서명 검증 전에는 인덱스 내용으로 어떤 파일도 받거나 쓰지 않는다.

인덱스에 `sequence`(정수, 1 이상, 안전한 정수)를 추가한다(1.2에서 필수). 같은 서버의 새 배포마다 Studio가 1씩 증가시킨다(`deploymentId`는 정렬 의미가 없는 기존 규칙 유지).

## 롤백 방지 (런처)
- 서버별로 지금까지 수락한 `{sequence, deploymentId, indexSha256}`의 최댓값을 서버 데이터 디렉터리 밖 런처 소유 상태(서버 데이터 삭제 시 함께 지울지는 구현에서 정하고 문서화: 기본은 서버 데이터 삭제 시 같이 삭제)에 원자적으로 저장한다.
- 새 배포의 sequence가 저장값보다 **작으면 거부**. 같으면 `deploymentId`와 인덱스 해시가 같을 때만 허용(재배포), 다르면 거부. 크면 파일 적용이 **성공한 뒤**에 갱신(실패한 적용으로 올리지 않음)하되, 적용 시작 전 거부 판정은 이미 끝나 있어야 한다.
- 저장 상태가 없으면(첫 설치, 삭제 후) 서명이 유효하면 수락한다.

## Studio 키 관리
- 개인 키는 앱 사용자 데이터 안에 Electron `safeStorage`로 암호화해 보관(프로젝트 폴더 밖, 프로젝트 `serverId`로 연결). `safeStorage`를 쓸 수 없는 환경이면 서명을 막고 명시 오류(평문 저장 금지).
- 백업/복원: 사용자가 고른 파일에 암호문으로 내보내기·가져오기(패스프레이즈 기반 scrypt + AES-256-GCM, 파일에 버전 필드). 키를 잃으면 새 키를 만들고 런처를 다시 내보내 전달해야 한다(기존 플레이어는 새 런처가 필요)는 경고를 Studio가 내보내기·키 생성 때 표시한다(UI 문구는 Studio UI 재작성 단계).
- `sequence`는 프로젝트 상태에 저장하고 배포 생성 때 +1. 배포 파일을 지우고 새로 만들어도 줄지 않는다.

## 작업 분할
1. **SIGN-CORE-01** (`packages/core/src/deployment/**`, `packages/core/src/server-config/**`, `docs/deployment-format.md`): 계약·검증(1.2, sequence), writer(서명 콜백 `sign(message): Buffer | Promise<Buffer>` 주입, 키는 core가 보관하지 않음), reader(공개 키 옵션, 검증 순서 강제, 서명 없음/오류/키 불일치 구분 오류), server-config의 `signing` 필드, 롤백 판정 순수 함수(저장은 앱). 변조·잘림·교차 서버·잘못된 키·재생·구버전 입력의 적대적 테스트 포함.
2. **SIGN-STUDIO-01** (`apps/admin` 메인/비UI, 1 이후): 키 생성·safeStorage 보관·백업/복원 함수, 배포 생성 시 서명과 sequence 증가, 내보내기 구성 파일에 `signing`. 렌더러 UI 변경 없음.
3. **SIGN-LAUNCHER-01** (`apps/launcher` 메인, 1 이후, 2와 병렬 가능): 구성의 공개 키를 reader에 전달, 롤백 상태 저장·판정·적용 성공 후 갱신, 새 실패 코드를 상태·i18n에 연결.
