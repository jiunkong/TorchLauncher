# 서버 파일 동기화 — SYNC-01 구현 기준

이 문서는 이번 코어 구현의 동작 기준이다. UI·사용자 모드 등록·혼합 설정 편집은 별도 작업이다.
입력은 신뢰된 서버 ID, 서버별 게임 루트, 검증된 deployment reader다.

사용자 요구에 따라 모드·리소스팩·설정 확장자나 고정 디렉터리 allowlist로 대상을 제한하지 않는다.
운영자는 서버 게임 폴더 안의 임의 상대 경로·파일 형식을 선택하고 파일별 적용 정책을 지정한다.
단축키·음량 등 자주 쓰는 설정의 전용 편집은 Studio/USER-02 편의 기능이며 범용 파일 동기화와 분리한다.

## 소유권과 비교

- 내부 상태와 transaction은 예약 경로 `.torchlauncher-sync/` 아래에 둔다.
  상태에는 버전·서버 ID·배포 ID·최초 구성 완료 여부와 경로/정책/해시/길이를 기록한다.
- `always`: 이전 관리 목록에 있는 파일만 수정·삭제할 수 있다. 로컬 내용이 최신 해시와 같으면
  payload를 받지 않는다. 누락·손상·변경된 관리 파일은 배포 내용으로 복구한다.
- 새 always 경로에 미등록 파일이 있으면 같은 내용이어도 자동 편입·덮어쓰기하지 않고 충돌을 반환한다.
  사용자 추가 모드 등록이 구현되기 전에도 미등록 파일을 보존한다.
- `initial-only`: 최초 성공한 환경 구성에서만 제공한다. 이미 있는 일반 파일은 보존한다.
  이후 추가된 기본 파일도 자동 적용하지 않으며, 사용자가 수정·삭제한 파일은 복구하지 않는다.
  배포에서 빠진 최초 기본 파일도 삭제하지 않는다. 최초 구성 완료는 성공한 transaction에만 기록한다.
- 이전 관리 목록의 always 파일이 새 배포에서 빠지면 삭제한다. 다른 파일·빈 디렉터리는 임의 정리하지 않는다.
  같은 경로의 정책 전환과 대소문자만 다른 경로 재사용, 파일↔디렉터리 전환은 이번에는 명시 충돌로 거부한다.
  자동 전환·사용자 데이터 이동 UI는 후속 범위다.
- 상태가 없거나 손상된 경우 파일을 스캔해 운영자 소유권을 재구성하지 않는다. 손상 상태는 오류로 중단한다.

## 경로와 동시 실행

- 같은 루트를 쓰는 기존 `acquireServerDataLock(root, 'maintenance')`로 설치·게임 실행·다른 동기화를 배제한다.
- 서버 ID와 모든 인덱스/상태/journal 경로를 검증한다. 루트와 부모/대상 symlink, 일반 파일이 아닌 대상,
  하드링크 파일을 거부한다. 파일명 충돌 규칙은 deployment 계약과 동일하게 적용한다.
- Java·Minecraft 설치 및 런처 데이터는 배포 대상이 아니다. 최소한 최상위 `runtime`, `versions`,
  `libraries`, `assets`, `natives`, `accounts`, `public-java`와 `.torchlauncher`로 시작하는 경로를
  보수적인 충돌 키로 보호한다. 이는 설치 엔진/인증/런처 내부 소유권 경계이며 콘텐츠 경로 allowlist가 아니다.
  `saves`·임의 모드 데이터·사용자 정의 디렉터리도 일반 파일과 같은 소유권·충돌 규칙으로 다룬다.
  인덱스뿐 아니라 과거 상태와 복구 journal에도 같은 보호 규칙을 적용한다.
- 목적은 원격 입력·기존 위험 경로·협력 프로세스 경합 방어다. 로컬 공격자가 파일 시스템을 동시에
  교체하는 적대적 TOCTOU나 모든 OS의 reparse point 방어를 완전 보장한다고 주장하지 않는다.

## 다운로드·적용·복구

- 계획을 먼저 만들고, 필요한 파일만 reader를 통해 내부 staging으로 받는다. 길이·해시·압축 검증이
  전부 끝나기 전에는 기존 게임 파일을 바꾸지 않는다. 취소·소스 변경·해시 오류 시 기존 환경을 보존한다.
- 적용 전 원본 상태를 다시 검사한다. 기존 파일을 같은 볼륨의 backup으로 보관하고 새 파일을 rename한다.
  삭제도 backup 이동으로 수행한다. 상태 파일은 같은 transaction의 마지막 단계에서 반영한다.
- mutation 전에 복구 가능한 bounded journal을 저장한다. 실패 시 이전 파일과 상태로 rollback하고,
  rollback 불가 시 backup/journal을 보존하며 복구 필요 오류를 반환한다. 모호한 상태에서 덮어쓰지 않는다.
- 다음 동기화 전에 남은 journal을 검사한다. commit 완료 여부에 따라 안전하게 rollback 또는 cleanup하며
  journal을 임의 경로 삭제 지시로 사용하지 않는다. 검증되지 않은 내부 파일은 재귀 삭제하지 않는다.
- 프로세스 종료 후 남은 서버 잠금의 자동 회수는 GAME-05다. 기존 잠금을 훔치지 않으며, 잠금 복구 후
  SYNC 복구가 가능하다. 실제 전원 차단·파일 시스템 내구성 보장은 이번 단위 검사와 구분한다.
- 진행률과 결과는 다운로드·재사용·기본값 보존·삭제 수를 구분한다. 원격 URL·비밀 정보를 journal에 넣지 않는다.

## 검증과 실파일

writer→HTTPS source→reader→sync 통합으로 최초 구성, 무변경 시 payload 0, 한 파일 변경만 전송,
관리 파일 삭제·손상 복구, initial-only 수정/삭제 보존, 미등록 파일 충돌, 정책 전환 거부,
서버 불일치, 위험 경로, 취소, 원격 교체, 적용 실패와 남은 journal 복구를 검증한다.

기존 Drive 검증은 임의 파일의 Range·버전 교체 증거다. 새 torchpack의 Drive 통합 실검증을 위해서는
코어로 생성한 작은 비민감 v1/v2 파일을 준비하고 #0이 사용자에게 업로드를 요청한다.
업로드·URL이 없더라도 로컬/모의 검사와 실환경 대기를 구분해 기록한다.
