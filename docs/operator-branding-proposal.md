# 운영자 브랜딩 계약 제안

**상태: 사용자 결정 대기.** 지금은 설계 제안만 기록한다. 승인 전에는 서버 설정 스키마, 런처 IPC/UI, Studio를 바꾸지 않는다.

## 현재 경계

런처는 시작 시 `TORCH_SERVER_CONFIG`가 있으면 그 경로를, 없으면 Windows portable 실행 파일 폴더(`PORTABLE_EXECUTABLE_DIR` 우선), Linux AppImage 폴더, 또는 실행 파일 폴더에서 `torchlauncher-server.json`을 찾는다. `bootstrap.ts`는 링크·하드링크·16 KiB 초과 설정을 거부하고 `parseServerConfig`에 전달한다. 파서는 현재 여섯 필드와 선택적 `game`만 허용하며 알 수 없는 필드는 거부한다. 따라서 `branding` 추가는 기존 런처와의 계약 호환성 문제다.

현재 Studio의 `exportLauncher`는 선택된 기존 EXE/AppImage와 설정 JSON을 빈 폴더에 복사한다. ZIP을 만들거나 자산을 복사하지 않는다. 사용자가 ZIP으로 묶는 과정은 향후 배포 흐름이며 구현된 것으로 안내하면 안 된다. 프로젝트 계약(`apps/admin/src/shared/studio.ts`)과 `parseProject`는 필드 집합도 엄격히 고정한다. Studio의 브랜딩 화면/자산 가져오기도 미구현이다.

## 이미지 전달 선택지

**A. 배포물 옆 로컬 파일(권장):** 설정 파일의 상대 경로로 `branding/icon.png`, `branding/background.png`를 참조하고, 운영자가 portable 실행 파일·설정·자산을 한 폴더에 둔 뒤 ZIP으로 전달한다. 첫 실행에 네트워크가 필요 없고 EXE 재빌드도 필요 없다. 현재 폴더 내보내기를 확장해 자산을 복사하고, 사용자가 폴더를 ZIP으로 배포하는 흐름에 맞는다. 자산 수정은 새 ZIP 재전달이 필요하다. 파일이 로컬이라고 해서 향후 업데이트가 불가능한 것은 아니다.

**B. torchpack에 포함:** 게임 파일과 같은 배포 컨테이너에서 자산을 가져온다. 매니페스트/동기화 상태에 자산 소유권과 캐시 정책을 추가해야 하고, 초기 구성 전에는 브랜딩을 표시할 수 없다. 파일 정책과 업데이트 의미도 섞여 현재 배포 계약에 부담이 크다.

**C. 독립 HTTPS URL:** 설정에는 URL만 두고 시작 시 내려받아 캐시한다. 운영자가 ZIP을 다시 배포하지 않아도 되지만, 첫 실행 네트워크 의존·다운로드/리다이렉트/캐시 만료 정책이 생긴다. URL은 해시가 콘텐츠를 고정하지 않으며, 해시를 함께 둬도 그 해시를 담은 설정 배포가 필요하다. 원격 변경을 허용할지 고정할지 별도 결정이 필요하다.

초기 부팅이 오프라인에서도 가능하고 Studio의 현재 폴더 내보내기에 가장 적게 개입하므로 A를 제안한다. 이는 이미지가 이후 영원히 바뀔 수 없다는 결정이 아니다.

## 승인 후 논의할 최소 계약

설정 v1의 선택 필드 `branding`에 `appName`(최대 40자, 제어문자 금지), `icon`, `background`를 둔다. 이미지 항목은 `{path, sha256, length}`로 하고, 경로는 배포 루트 기준 NFC 슬래시 상대경로만 허용한다. 아이콘 PNG, 배경 PNG/JPEG를 후보로 두며, 실제 디코더 지원은 구현 때 확인한다. 아이콘 최대 1 MiB/512×512, 배경 최대 8 MiB/3840×2160, 디코드 픽셀 상한 8,294,400을 제안한다. 수치는 확정값이 아닌 검토용 상한이다. 파일 크기·SHA-256·실제 디코드 및 픽셀 수를 확인하고, 링크/하드링크/루트 이탈을 거부해야 한다. 해시는 무결성 확인이지 운영자 진위 증명은 아니다.

메인 프로세스가 설정 루트를 기준으로 제한된 자산을 읽고 검증한 뒤 렌더러에 필요한 이미지 데이터만 넘기는 방식이 기본안이다. 기존 `index.html` CSP의 `img-src 'self' data:`가 data URL은 허용한다. 큰 배경을 IPC에 싣는 비용과 로컬 프로토콜/CSP 확대는 구현 전에 비교한다. 메인에서 네이티브 창 아이콘도 적용할 수 있다. `appName`은 창 제목과 운영자 메뉴 아이콘 주변 표시에만 쓴다. `app.setName`, appId, 사용자 데이터·인증 캐시 위치, 패키지 EXE 메타데이터는 건드리지 않고, 기존 `name`(홈의 서버 이름)과 시작 화면의 TorchLauncher 브랜드도 유지한다. 누락된 선택 자산은 기본 `assets/branding/icon.png`와 CSS 기본 배경으로 대체하는 안이다. 자산이 선언됐지만 경로·해시·디코드 검증에 실패하면 선택 필드를 기본값 처리할지, 전체 설정 오류로 표시할지는 승인 때 확정한다.

새 필드를 모르는 이전 런처는 엄격 파서에서 설정 전체를 거부한다. 새 런처는 필드가 없는 기존 프로파일을 계속 읽을 수 있다. 따라서 브랜딩을 포함한 ZIP의 최소 런처 버전 요구/업그레이드 안내가 필요하지만 현재 최소 버전 계약은 구현돼 있지 않다. v1 설정에 알 수 없는 필드를 조용히 무시하도록 바꾸는 호환 전략도 승인 후 선택해야 한다.

Studio는 먼저 계약과 런타임 경로를 승인·구현한 뒤, 다음 단계에서 이미지 파일 선택/미리보기와 내보내기 자산 복사를 추가하는 순서를 제안한다. 로컬 자산을 수정하면 프로파일과 이미지를 포함한 ZIP을 다시 전달해야 한다. 원격 자동 브랜딩은 별도 후속 기능으로 남길 수 있다. 사용자 승인 전에는 양 단계 모두 착수하지 않는다. EXE 아이콘 변경, 코드 서명, 시작 화면 변경은 이번 제안 범위가 아니다.
