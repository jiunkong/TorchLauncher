# TorchLauncher 설계

이 문서는 지금까지 합의한 제품 방향과 아키텍처를 정리한다. 두 앱의 초기 실행 기반과 배포 계약·Range 전송·인증·Minecraft 설치 코어가 있으며 앱 연결과 실제 계정·게임 검증은 후속 작업이다. 아래 제품 기능 전체의 구현 완료를 의미하지 않는다. 확정된 v1 배포 규격은 [deployment-format.md](deployment-format.md), 미결정 사항은 마지막 절, 실행 명령은 루트 README, 현재 상태는 [progress.md](progress.md)를 참고한다.

## 1. 목표와 지원 범위

프로젝트 이름은 **TorchLauncher**로 확정한다. 사용자 런처는 **TorchLauncher**, 운영자 관리 앱은 **TorchLauncher Studio**로 구분한다. 저장소·패키지 등 소문자 식별자가 필요한 곳에서는 `torchlauncher`를 기본 이름으로 사용한다.

운영자가 관리 앱에서 서버 환경을 구성하고 전용 런처를 내보내면, 사용자는 전달받은 파일을 실행하고 최초 Microsoft 로그인 후 접속 버튼만으로 설치·업데이트·서버 접속을 완료한다.

- Windows, macOS, Linux를 지원한다.
- 개인 서버 운영을 우선하되 다른 운영자도 자신의 서버용으로 사용할 수 있게 한다.
- Minecraft 버전과 로더는 운영자가 선택한다.
- 초기부터 Fabric과 NeoForge를 모두 지원한다.
- 첫 검증 환경은 Minecraft 1.21.1 + NeoForge이며, Fabric도 초기 검증에 포함한다.
- Microsoft 정품 계정 로그인을 지원하고 로그인 상태를 유지한다.
- 운영자의 Google Drive 등 파일 배포 서비스 계정 연동은 지원하지 않는다. 운영자가 직접 업로드하고 공개 다운로드 링크를 입력한다.
- 지원 버전 선택 기능이 모든 Minecraft 버전과 모드 조합의 호환성을 보장하는 것은 아니다. 실제 지원·검증 범위는 명시한다.

## 2. 앱 구성과 기술 스택

Electron + TypeScript를 사용하고 UI는 React로 구성한다. OS별 패키징과 실제 실행 검증은 각각 수행한다. Electron을 포함하므로 게임 파일을 제외해도 런처 배포물 자체의 용량은 발생한다.

pnpm 워크스페이스 모노레포로 관리하되 두 앱은 독립적으로 실행·빌드·배포한다. 앱끼리 직접 의존하지 않고 배포 규격·계약·유틸리티를 공유한다. 공통 코어를 사용한다는 이유로 두 앱의 모든 기능을 함께 번들하지 않는다. Node.js 24, electron-vite, Vitest, Biome, electron-builder를 기반 도구로 사용한다.

| 구성 | 역할 |
| --- | --- |
| 관리 앱 | 서버 환경·이미지·기본 설정 구성, 원격 배포 파일 생성, 서버 전용 런처 내보내기 |
| 사용자 런처 | 로그인, 동기화, 서버 상태, 게임 실행, 사용자 추가 모드 관리, 데이터 삭제 |
| 공통 코어 | 배포 포맷, 다운로드, 해시 검증, Java·게임·로더 설치, 실행 환경 관리 |

저장소 구조는 다음과 같다. `mods/`에는 보조 모드 계획 철회 안내만 있으며 구현·빌드 프로젝트는 없다.

```text
apps/admin/       운영자 관리 앱
apps/launcher/    사용자 런처
packages/core/    공통 설치·다운로드·동기화 로직
mods/            보조 모드 계획 철회 안내
docs/            설계와 배포 규격
```

UI와 파일·네트워크·프로세스 작업은 제한된 IPC 인터페이스로 연결한다. 해시 계산과 압축 처리는 별도 작업 스레드 등으로 분리해 UI가 멈추지 않게 한다.

## 3. 전용 런처 내보내기

### 브랜드와 서버 전용 화면

- 앱 이름·아이콘·시작 로고는 프로젝트 공통 브랜드로 고정한다.
- 실행 후에는 해당 서버의 이름·이미지·접속 정보가 반영된 전용 화면을 제공한다.
- 사용자에게 서버 주소나 배포 링크를 다시 입력하도록 요구하지 않는다.
- 코어는 공통으로 유지하고 서버별 설정과 이미지로 전용 런처를 구성한다.

### 포터블 배포

- 설치형보다 포터블 배포를 기본으로 한다.
- 관리 앱은 미리 빌드된 OS별 공통 코어에 서버 설정과 이미지를 묶어 내보낸다.
- 운영자에게 서버마다 소스를 빌드하거나 개발 도구를 설치하도록 요구하지 않는 구조를 지향한다.
- 사용자에게 전달하는 파일에는 무거운 모드·리소스팩·게임 파일을 넣지 않는다. 필요한 파일은 실행 후 원격에서 받는다.
- 정확한 OS별 패키지 형식, CPU 아키텍처 지원, 서명 방식은 후속 설계에서 확정한다.

### 운영자 흐름

1. 관리 앱에서 서버 이름·이미지·주소와 Minecraft·로더 버전을 지정한다.
2. 배포할 클라이언트용 모드·리소스팩·설정과 적용 정책을 구성한다.
3. 관리 앱으로 단일 배포 파일을 생성한다.
4. 파일 공유 서비스에 직접 업로드하고 공개 다운로드 링크를 등록·검사한다.
5. 해당 링크가 포함된 OS별 전용 런처를 내보내 사용자에게 전달한다.
6. 이후 게임 환경 업데이트는 같은 원격 파일의 내용을 교체해 배포한다.

## 4. 자동 설치와 설정 동기화

### 실행 환경

- 지정된 Minecraft·로더 및 호환 Java를 자동 설치한다.
- 기존 `.minecraft`와 분리된 서버별 환경을 사용한다.
- 포터블 실행 파일과 별개로, 게임 데이터는 OS 사용자 데이터 폴더 아래에 서버별로 보관한다.
- 실행 파일을 옮기거나 교체해도 같은 서버의 데이터를 이어서 사용할 수 있도록 안정적인 서버 식별자가 필요하다.

### 설정 적용 정책

| 정책 | 용도 | 적용 방식 |
| --- | --- | --- |
| 최초 기본값 | 단축키·음량·화면 설정 등 개인 설정 | 최초 환경 구성 시 제공하고 이후 사용자 변경 보존 |
| 계속 동기화 | 서버 접속에 필요한 모드와 필수 설정 | 운영자의 최신 배포본에 맞춰 관리 |

운영자는 단축키 같은 설정도 미리 구성할 수 있다. 리소스팩은 파일 배포뿐 아니라 운영자가 의도한 적용 상태를 구성할 수 있어야 한다. 개인 설정과 필수 설정이 같은 파일에 섞여 있으면 파일 전체 덮어쓰기로 해결하지 않고 항목별 적용 방식을 별도로 설계한다.

### 모드 소유권

- 운영자 배포 파일과 사용자 추가 모드를 별도 목록으로 관리한다.
- 사용자는 런처를 통해 추가 모드를 등록·삭제한다.
- 사용자 추가 모드는 서버 업데이트 후에도 보존한다.
- 운영자 배포에서 빠진 파일은 이전 운영자 관리 목록을 기준으로 제거한다.
- 어느 목록에도 없는 파일은 미등록 파일로 구분하고 정리 대상으로 표시한다. 사용자 모드로 자동 분류하거나 즉시 삭제하지 않는다.
- 사용자 모드와 운영자 모드의 호환성을 자동으로 보장하지 않는다. 실행 실패 시 오류와 로그를 확인할 수 있게 한다.
- 경로 또는 모드 ID가 충돌하는 경우의 처리 정책은 구현 전에 확정한다.

## 5. 단일 파일 배포와 부분 다운로드

### 채택한 방식

최신 배포 파일 하나에 앞부분 인덱스와 파일별 데이터를 넣는다. 런처는 인덱스를 먼저 읽고 로컬 해시와 비교해 필요한 데이터 구간만 HTTP Range로 다운로드한다.

```text
[식별자 · 포맷 버전 · 인덱스 길이]
[배포 정보 · 파일별 인덱스]
[파일 A 데이터]
[파일 B 데이터]
[파일 C 데이터]
```

인덱스에는 다음 정보가 필요하다. 정확한 필드명과 바이너리 표현은 아직 확정하지 않았다.

- 서버·배포 식별자와 Minecraft·로더 버전.
- 파일별 상대 경로와 SHA-256 해시.
- 데이터 위치, 저장 길이, 원본 길이, 압축 방식.
- 최초 기본값 또는 계속 동기화 적용 정책.

각 파일을 독립적으로 압축하거나 원본 그대로 저장한다. 전체 데이터를 하나의 연속 압축 스트림으로 만들지 않는다. 이미 압축된 JAR·ZIP은 추가 압축 없이 저장할 수 있다.

### 사용자 다운로드 흐름

1. 앞부분의 고정 길이 영역을 받아 인덱스 길이를 확인한다.
2. 인덱스를 받아 로컬 파일과 해시를 비교한다.
3. 변경·누락·손상된 파일의 데이터 구간만 요청한다.
4. `206 Partial Content`, `Content-Range`, 실제 수신 길이를 검증한다.
5. 필요 시 압축을 풀고 파일 해시를 검증한다.
6. 필요한 다운로드와 검증이 끝난 뒤 실행 환경에 적용한다.
7. 운영자 관리 목록에서 제거된 파일을 정리한다.

| 상태 | 전송하는 데이터 |
| --- | --- |
| 최신 환경 | 앞부분과 인덱스 |
| 일부 변경·손상 | 인덱스와 해당 파일 데이터 |
| 최초 설치 | 인덱스와 설치에 필요한 전체 파일 데이터 |

앞부분만 읽고 연결을 끊는 방식은 변경 여부 확인에 사용할 수 있지만, 중간 구간만 전송받으려면 배포처의 Range 지원이 필요하다. 파일 단위 변경 감지이므로 변경된 모드 하나는 해당 모드 파일 전체를 받는다.

과거 변경분 ZIP, 파일별 공유 링크, 별도 최신 버전 안내 파일을 유지하는 방식은 기본 구조로 사용하지 않는다. 운영자는 최신 단일 배포 파일을 관리한다.

### 오류와 일관성

- Range 요청이 무시되면 전체 다운로드로 조용히 전환하지 않고 이유를 표시한다.
- 다운로드 재시도·취소·진행률과 실패 원인을 제공한다.
- 검증 전에는 기존 환경을 덮어쓰지 않는다. 실패 후 복구 가능한 적용 절차를 설계한다.
- 다운로드 중 원격 파일이 바뀌면 이전 인덱스와 새 데이터가 섞이지 않도록 변경을 감지하고 인덱스부터 다시 확인한다.
- 가능하면 ETag 등 서버의 버전 식별자를 활용한다. 제공되지 않는 경우의 일관성 검증도 별도로 설계한다.
- 경로 이탈, 잘못된 범위·길이, 비정상 압축 크기와 해시 불일치를 거부한다.

## 6. Google Drive와 일반 HTTPS

일반 HTTPS 다운로드를 기반으로 하며 Google Drive 공개 공유 링크도 처리한다. 운영자와 사용자에게 Google 로그인을 요구하지 않는다.

### 고정 링크

Drive에서는 기존 파일을 삭제하고 새 파일을 만드는 대신 **버전 관리 → 새 버전 업로드**로 내용을 교체한다. 같은 파일의 공유 링크·파일 ID를 유지하는 운영 방식으로 정한다.

```text
고정 공유 링크 / 파일 ID
    → 실제 다운로드 주소 확인
    → 인덱스 Range 요청
    → 변경된 데이터 구간 요청
```

런처에는 공유 링크와 파일 ID를 보관하고 실제 다운로드 주소는 필요할 때 다시 얻는다. 확인 페이지, 리다이렉트, 다운로드에 필요한 익명 세션을 처리한다.

### gdown 코드 활용

- MIT 라이선스의 gdown에서 공개 URL 해석·확인 페이지·다운로드 주소 획득 로직을 가져와 TypeScript로 이식한다.
- Python 런타임을 포함하지 않는다.
- 계정 연동이나 브라우저 로그인 쿠키 가져오기 기능은 포함하지 않는다.
- 출처와 원본 커밋을 기록하고 저작권·MIT 라이선스 고지를 포함한다.
- 링크 해석과 자체 Range 다운로드·배포 포맷 처리를 분리한다.

### 확인된 사실과 남은 검증

사용자가 `drive.usercontent.google.com` 다운로드 링크에 curl로 Range 요청을 보내 `206`과 요청 구간 데이터가 반환되는 동작을 확인했다. 이는 사용자 테스트 결과이며, 저장소에서 재현한 자동 테스트 결과는 아니다.

공유 링크 해석부터 새 버전 교체까지의 전체 흐름, 대용량 확인 페이지, 익명 접근, 다운로드 제한·만료 후 재시도는 추가 검증한다. 관리 앱의 URL 검사에서도 실제 부분 요청과 응답 내용을 확인한다.

## 7. 서버 상태·게임 접속·종료

- 런처에 서버 접속 가능 여부·접속 인원·지연시간을 표시한다.
- 응답이 없다는 이유만으로 서버 종료를 단정하지 않도록 확인 실패 상태를 구분한다.
- 실행 버튼을 누르면 동기화 후 메인 메뉴 조작 없이 지정 서버에 접속한다.
- 직접 접속은 해당 버전에서 지원하는 실행 인자를 사용한다. 1.20 이상 정식 버전은 Quick Play, 1.7.10 등 기존 인자 지원 버전은 `--server`·`--port`를 사용하며 실제 로더·모드 조합으로 검증한다. 구버전 설치·실행 지원은 아직 구현하지 않았다.
- 연결 해제 시 게임 자동 종료는 제품 범위에서 제외한다. 이를 위한 보조 모드도 개발하지 않는다. 사용자의 연결 해제·강퇴·통신 오류 후 화면과 종료 동작은 게임 기본 동작을 따른다.
- 런처가 확인할 수 있는 설치·실행 오류와 프로세스 종료 상태를 표시한다.
- 사용자에게 이해 가능한 오류 설명과 로그 열기·내보내기를 제공한다.

## 8. 로컬 데이터 관리

- 런처에서 서버별 데이터 경로와 사용 용량을 확인할 수 있게 한다.
- 서버 데이터 삭제 기능을 제공하고 삭제 전에 대상과 용량을 표시한다.
- 게임 실행 중에는 해당 서버의 데이터 삭제를 막는다.
- 삭제 범위는 선택한 서버 데이터로 제한한다. 다른 서버, 기존 `.minecraft`, 공유 계정 자격 증명까지 함께 삭제하지 않는다.
- 인증 토큰·배포처 자격 증명 등 비밀 정보를 저장소나 배포물에 포함하지 않는다. Microsoft 세션의 안전한 저장 방식은 인증 구현 시 확정한다.

## 9. 검증 기준

- Windows·macOS·Linux에서 포터블 실행과 서버별 데이터 분리를 확인한다.
- 1.21.1 NeoForge와 Fabric에서 Java·게임·로더 설치 및 서버 직접 접속을 확인한다.
- 최초 단축키 적용 후 사용자가 변경한 값이 업데이트에도 보존되는지 확인한다.
- 사용자 모드 등록·삭제·보존과 운영자 모드 제거·미등록 파일 구분을 확인한다.
- 변경이 없을 때 인덱스만, 변경이 있을 때 필요한 데이터 구간만 받는지 확인한다.
- 신규 설치·손상 복구·취소·재시도·잘못된 Range 응답·다운로드 중 원격 교체를 검증한다.
- Drive의 기존 파일에 새 버전을 올린 뒤 같은 공유 링크로 새 인덱스와 중간 구간을 받는지 확인한다.
- 서버 직접 접속과 게임 프로세스 종료 상태 처리를 검증한다. 연결 해제를 이유로 게임을 자동 종료하지 않는다.
- 서버 데이터 삭제가 다른 환경에 영향을 주지 않는지 확인한다.

## 10. 구현 전에 확정할 사항

다음은 아직 결정하지 않은 항목이다. 확정된 요구사항이나 구현된 기능으로 취급하지 않는다.

- 배포 포맷 v1의 서명·발행자 신뢰·이전 배포본으로의 되돌리기 방지 정책. 현재 해시는 손상 검사용이며 배포자의 HTTPS 주소를 신뢰한다.
- 로컬 파일 관리 목록, 실패 복구·적용 절차의 구체적인 구조. 서버 식별자는 배포 규격의 UUID v4 계약을 따른다.
- 혼합 설정 파일의 항목별 적용과 리소스팩 활성화·순서 관리.
- 사용자 모드와 필수 모드의 파일 경로·모드 ID 충돌 처리.
- Microsoft 앱 등록과 API 접근 조건, 시스템 브라우저·OS 안전 저장 어댑터와 실제 로그인·갱신 검증. 인증 코어의 모의 응답 검증과 구분한다.
- 지원 Minecraft 버전 목록과 로더별 설치·직접 접속 대응 범위.
- OS·CPU 아키텍처별 포터블 패키지, 서명 및 런처 코어 자동 업데이트.
