# TorchLauncher 구현 순서

각 단계는 기능 구현과 해당 검증을 함께 완료한다. 실제 OS·계정·서버 검증이 필요한 항목은
자동 테스트와 구분해 기록한다. UI가 있어도 실제 기능이 없으면 제공 중인 기능으로 표시하지 않는다.

작업 상태·담당 에이전트·브랜치·검증·머지 기록은 [개발 진행 관리](progress.md)에서만 갱신한다.
이 문서는 구현 순서와 단계별 목적을 설명한다.

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| 1. 프로젝트 기반 | pnpm 모노레포, 독립 Electron 앱, 공유 계약, 검사·빌드·패키징·CI | 로컬 검사와 실행 확인, OS별 검증 경로 마련 |
| 2. 핵심 기술 검증 | gdown 공개 링크 처리 이식, Drive Range·파일 교체, Microsoft 인증 | 같은 공유 링크로 새 배포본 일부 수신, 정품 계정 인증 |
| 3. 배포·동기화 코어 | 인덱스 규격, 생성·읽기, 해시 비교, 부분 다운로드, 실패 복구 | 변경 파일만 다운로드하고 검증 후 적용 |
| 4. 게임 실행 코어 | Java·게임 설치, NeoForge와 Fabric, 서버 직접 접속 | 1.21.1에서 두 로더로 실제 서버 접속 |
| 5. 사용자 환경 관리 | 최초·필수 설정, 추가 모드 목록, 데이터 삭제, 종료 보조 모드 | 개인 설정과 추가 모드 보존, 직접 나가기 시 종료 |
| 6. 사용자 런처 | 서버 전용 화면, 인증·접속, 상태, 진행률, 오류·로그 | 초기 실행부터 업데이트·서버 접속까지 연결 |
| 7. Studio·배포 | 프로젝트 저장, 환경 편집, 배포 파일 생성, URL 검사, 전용 런처 내보내기 | 운영자가 개발 도구 없이 전용 런처 생성 |

서명과 런처 코어 자동 업데이트는 기본 배포 흐름과 별도로 구체화한다.
기능 단계 중에도 OS별 빌드·실행 검증을 계속 유지한다.

## 기반 단계의 경계

- 사용자 런처와 Studio의 초기 화면 및 읽기 전용 앱 정보 IPC만 구현한다.
- 렌더러 Node.js 접근을 끄고 격리·샌드박스를 활성화한다.
- 공유 패키지의 소스는 앱 빌드에 번들하고, 앱끼리 직접 참조하지 않는다.
- 배포 파일 규격, 서버 설정 스키마, 게임 설치 로직은 다음 단계에서 설계·구현한다.
- Java 보조 모드는 독립 빌드 프로젝트로 둘 예정이며 아직 스캐폴딩하지 않는다.

기반 단계의 실제 검증 결과는 [개발 진행 관리의 검증·통합 기록](progress.md#검증통합-기록)을 참고한다.
